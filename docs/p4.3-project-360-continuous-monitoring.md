# P4.3 — Project 360 Continuous Monitoring

## 1. Goal

P4.3 turns a completed Project 360 report into an owner-controlled monitored
project. A monitor repeats the same explicitly confirmed source set and the same
selected paid modules on a manual, daily, or weekly cadence. Every successful
cycle produces a new immutable Project 360 report, canonical hash, Aggregate Arc
proof, delta report, and history point in one stable `vtr_` Trust Profile.

P4.3 does not change the accepted Discovery → Quote → Execution architecture and
does not create a new workflow. It orchestrates the existing `project_360`
workflow through a monitoring-specific ledger.

## 2. Product boundaries

- A monitor can be created only from an owner-scoped, completed, canonically
  valid Project 360 report with a verified Aggregate Arc proof.
- The immutable configuration contains the confirmed source value hashes and the
  selected module set from that report.
- Every recheck creates a new immutable quote and one Project 360 job. Manual
  rechecks retain the normal sponsored-or-paid checkout. Scheduled rechecks use
  the existing bounded `scheduled_monitoring` sponsorship path.
- Provider purchases remain project-owned and budget bounded. User accounting
  remains separate from downstream x402 payments.
- Missing or failing modules are represented by their normalized Project 360
  statuses and never become zero scores.
- Arc remains testnet-only. A snapshot is `verifiedOnArc` only when the Aggregate
  proof whose response hash equals the canonical report hash is included in an
  Arc block.

## 3. Architecture

```text
Completed Project 360 report
        │ explicit “Monitor” action
        ▼
Project 360 monitor
  ├─ immutable selected modules
  ├─ immutable confirmed-source hashes
  ├─ owner cadence / visibility
  └─ stable vtr_ Trust Profile
        │
        ├─ manual quote → normal confirmation
        └─ due scheduler → sponsored monitoring quote
                    │
                    ▼
          exact-source execution discovery
          (server clone; no new candidates)
                    │
                    ▼
          Project 360 Quote → one Job
                    │
                    ▼
          Canonical report + Aggregate Arc proof
                    │
                    ▼
          Snapshot → Delta → Alert → Webhook

Free rediscovery runs after a snapshot on a separate plane:
new candidate → private suggestion → explicit Project 360 review
              (never added to quote or execution automatically)
```

## 4. Storage

### `project_360_monitors`

Stores tenant ownership, stable profile binding, baseline report references,
immutable Project 360 input, selected modules, sorted source value hashes, a
public-safe selected-candidate snapshot, cadence, visibility, and the latest
snapshot/job/error pointers. A database trigger rejects updates to the immutable
configuration.

### `project_360_monitor_rechecks`

One row per baseline/manual/scheduled cycle. The unique
`(monitor_id, idempotency_hash)` key and unique quote/job bindings make replay
return the original artifacts. The row also binds the configuration hash used to
create its quote.

### `project_360_monitor_snapshots`

One immutable canonical report per job and sequence. It stores only public-safe
Project 360 report/delta payloads plus score, confidence, coverage, report hash,
verification status, and Aggregate Arc transaction hash.

### `project_360_monitor_suggestions`

Stores candidates found by free rediscovery for modules outside the fixed set.
Candidates are private to the owner, default to `pending`, and expose provenance
and confidence. Dismissal is supported. Inclusion requires returning to the
normal Project 360 Discovery/Quote flow and creating a newly reviewed monitor.

## 5. Idempotency and scheduling

1. Saving the same owner/selection returns the existing monitor.
2. Baseline capture is unique by Project 360 job.
3. A recheck idempotency key is bound to the monitor configuration hash.
4. The quote is created from a server-side clone containing only the previously
   confirmed candidate snapshot. No current rediscovery result participates.
5. The scheduled launch RPC locks the monitor/recheck/quote, verifies workflow,
   tenant, sponsorship, module set and sorted source value hashes, then creates
   exactly one payment record and one job.
6. Replays return the existing quote/job/snapshot and do not publish a second
   proof or charge again.
7. Daily/weekly claims use `FOR UPDATE SKIP LOCKED`; active-job policy remains
   global and fail closed.

## 6. Delta Report

`veyra.project360.delta.v1` compares canonical reports and includes:

- Project Trust Score, confidence, coverage, and verdict changes;
- module status and module score changes;
- new and resolved evidence-backed risks;
- GitHub activity/release/security signal changes;
- treasury balance, runway, concentration, and recurring-flow changes;
- contract code/proxy/admin/owner/pause changes;
- API quality score, availability, latency, execution, payment and settlement
  changes when the module has sufficient evidence;
- Agent Trust score/status/identity/execution/payment/service/contract changes.

The implementation emits deterministic stable codes and public-safe before/after
values. A delta is meaningful when the score moves by at least five points, a
risk appears or resolves, a verdict/module status changes, or a module-specific
critical signal changes.

## 7. Alerts and webhooks

Meaningful Project 360 deltas reuse the existing tenant-scoped alert states,
signed webhook events, bounded delivery retry, SSRF protection, and subscription
profile filters. Payloads contain the `vtr_` profile, public snapshot ID, score,
coverage, Arc verification state and public-safe change only. They exclude owner
wallet, credentials, quote/payment/job IDs, provider internals, raw inputs and raw
errors.

## 8. Public and private views

`/monitoring` is the private control plane: save a completed Project 360 job,
change cadence/visibility, run a fresh quote, inspect suggestions, pause, or
delete.

`/trust/[publicId]` is the fail-closed public proof plane: current Project Trust
Score, coverage/confidence, selected module statuses, score history, meaningful
delta timeline, full-report links, and one Aggregate Arc proof per snapshot.
Private and unknown profiles return the same 404.

## 9. Security review

- Source substitution: fixed source hashes and module set are verified in both
  application code and the scheduled-launch RPC.
- Hidden charges: every manual cycle exposes a new itemized quote; scheduled
  cycles are explicitly labelled sponsored monitoring and cannot fall through to
  a user charge.
- Automatic expansion: rediscovery writes suggestions only; execution cloning
  reads the immutable selected-candidate snapshot only.
- SSRF: confirmed HTTPS endpoints are revalidated by the existing Project 360
  quote path before every execution.
- Privacy: all Project 360 monitoring tables are service-role only with RLS;
  public projections omit tenant, cron, quote, payment and credential fields.
- Proof integrity: snapshot report hash must equal the canonical Project 360 hash
  and the matched proof response hash. Arc deterministic finality requires one
  included confirmation.
- Failure isolation: a provider/module failure produces limited coverage without
  replacing completed module results or inventing data.

## 10. Acceptance criteria

- A completed verified Project 360 report can seed one idempotent monitor and
  baseline snapshot.
- Manual/daily/weekly are supported and the fixed module/source configuration is
  database immutable.
- Every recheck has one quote, one payment accounting row, one job, one snapshot,
  and one matching Aggregate Arc proof.
- Same-key replay returns the same artifacts; changed payload returns conflict.
- A rediscovered unselected module becomes a private pending suggestion and is
  never present in the current or next execution plan without a new explicit
  Project 360 review.
- Delta formulas cover score, risk, GitHub, treasury, contract, API and Agent
  changes without leaking module internals.
- Meaningful changes create one idempotent alert and signed webhook event.
- Private/foreign monitors and profiles fail closed with 404.
- Old Agent Trust profiles, snapshots, alerts and webhooks remain compatible.
